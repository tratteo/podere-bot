# PodereBot

Telegram bot for gates, heating, temperatures and sensors on a Raspberry Pi. ASP.NET Core, systemd.

## Requirements

.NET 10 SDK, `git`, `curl`, systemd (Linux). On the Raspberry Pi:

```sh
curl -sSL https://dot.net/v1/dotnet-install.sh -o /tmp/dotnet-install.sh
chmod +x /tmp/dotnet-install.sh
sudo /tmp/dotnet-install.sh --channel 10.0 --install-dir /usr/share/dotnet
sudo ln -sf /usr/share/dotnet/dotnet /usr/local/bin/dotnet
dotnet --info
```

## Install

```sh
git clone <repo-url> PodereBot
cd PodereBot
sudo ./install.sh   # creates a .env template and stops
nano .env           # fill TELEGRAM_API_KEY and ZEN_API_KEY
sudo ./install.sh   # builds, installs and starts the services
```

The bot starts at boot as `poderebot.service`. A watchdog checks `/api/health` every 10 minutes.

The touch panel is served by the same process. On the Pi the HDMI screen opens `http://127.0.0.1:5051/panel/` in `cage` + `cog` through `poderebot-kiosk.service`; authorised tablets and phones use the LAN port `http://<pi>:5052/panel/` after a one-time pairing link. `install.sh` needs `cage` and `cog` (`sudo apt install cage cog`).

## Update

```sh
cd ~/PodereBot
sudo ./install.sh
```

One command does everything: fetch and reset to `origin/release`, build fresh, install or update the systemd units and sudoers rule, write `.install-state`, stop once, swap `build.next` into `build`, start once, wait for `/api/health` and roll back on failure. Runtime state (`.env`, `db.json`, `users.json`, `usage.json`, `panel.db`) is never part of the swap.

```sh
sudo ./install.sh --check          # running vs release SHA, changes nothing
sudo ./install.sh --dry-run        # show what would happen
sudo ./install.sh --branch main    # test another branch
sudo ./install.sh --ref <sha>      # deploy a precise commit
sudo ./install.sh --no-pull        # build the current checkout, local changes allowed
```

`patch.sh` no longer exists. `install.sh` is the only deployment path, manual or automatic.

## Automatic update

`install.sh` installs `poderebot-update.timer`, which runs `sudo install.sh --auto` every 2 minutes (`UPDATE_INTERVAL` in `.env`).

`--auto`:

- follows `release`, which CI moves forward only after build and tests pass;
- installs changed units and the sudoers rule as well;
- builds beside the running service and swaps only when the SHA or the installation changed;
- writes `lastRunUtc` at every check, even when no update is available, so `Ultima verifica` in the panel always moves;
- writes `version.json` with the built SHA and UTC build time;
- rolls back the build if `/api/health` does not come back;
- never stops the service when the build fails.

```sh
sudo ./install.sh --check                 # manual check, same logic
journalctl -u poderebot-update.service -f
cat update-state.json
```

The panel shows the running SHA as `Versione`, the build time as `Aggiornato` and the last updater run as `Ultima verifica`.

## Uninstall

```sh
sudo ./uninstall.sh                                # services, timers, sudoers and build; data is kept
sudo ./uninstall.sh --purge                        # also removes .env, db.json, users.json and panel.db
sudo ./uninstall.sh --purge --delete-repo --yes    # removes the repository folder too
```

It stops and removes `poderebot.service`, `poderebot-wd.service`, `poderebot-wd.timer`, `poderebot-update.service`, `poderebot-update.timer` and `poderebot-kiosk.service`, together with their drop-ins, the updater sudoers rule, the generated scripts and `build/`. `--dry-run` prints every action without changing anything. `cage`, `cog` and the system user are left untouched.

## Service

```sh
sudo systemctl restart poderebot.service
sudo systemctl status poderebot.service --no-pager
journalctl -u poderebot.service -f
```

## Files

| Path | Tracked | Purpose |
|---|---|---|
| `.env` | no | secrets, overrides `appsettings.json` through environment variables |
| `appsettings.json` | yes | pins, heating, AI endpoint/model, `Users` seed |
| `users.json` | no | runtime users, entitlements and topic subscriptions managed by `/adminpanel` or the panel |
| `db.json` | no | runtime state (heating program, gate access, subscriptions) |
| `panel.db` | no | SQLite: hourly temperature history, event log and paired panel devices |
| `usage.json` | no | daily token usage used by `/status` |
| `panel.sh` | no | kiosk launcher generated by `install.sh` (`cage` + `cog`) |
| `panel-pair.sh` | no | creates the first panel device without the HDMI screen |

## Local panel demo

Preview the panel without touching the Pi and without sending Telegram messages:

```powershell
dotnet build -c Release
pwsh scripts/demo.ps1
```

The script creates a temporary content root with a seeded `panel.db` (local probe plus three sample sensors), sample version metadata and a fake Telegram token, then serves the panel at `http://127.0.0.1:5051/panel/#heating`. Stop it with `pwsh scripts/demo.ps1 -Stop`.

## Settings

`.env`:

```
TELEGRAM_API_KEY=...
ZEN_API_KEY=...
# SerialPort=/dev/ttyUSB0
```

Every `.env` key overrides the same key in `appsettings.json`.

`ZEN_API_KEY` is the OpenCode API key, valid for both Go and Zen.

### AI

```json
"AI": {
  "Endpoint": "https://opencode.ai/zen/go/v1/",
  "Model": "deepseek-v4.1-flash",
  "ReasoningEffort": "Low"
}
```

- `Endpoint`: `https://opencode.ai/zen/go/v1/` uses the Go subscription, `https://opencode.ai/zen/v1/` is Zen pay-as-you-go. The same key works for both.
- `Model`: any id from `https://opencode.ai/zen/go/v1/models`.
- `ReasoningEffort`: `None`, `Low`, `Medium`, `High` or `ExtraHigh`.
- `/status` reports the last 7 days of token usage and the estimated Go cost as a percentage of `WeeklyBudgetUsd`. Prices and time multipliers are fetched from `{Endpoint}models` every 6 hours; `InputPricePerMillion`, `CachedInputPricePerMillion` and `OutputPricePerMillion` are only fallbacks. Usage is kept in `usage.json`.
- Go requires the `x-opencode-session` header; the bot sends one per chat automatically.
- If the bot answers with the generic error, check `journalctl -u poderebot.service`: `api_key_expired` means the key in `ZEN_API_KEY` must be replaced with a new one from OpenCode Console.

Hardware defaults to embedded GPIO. Set `SerialPort` only if the pins are driven over a serial adapter.

### Heating and alerts

```json
"Heating": {
  "Antifreeze": { "Enabled": true, "ThresholdCelsius": 5.0 },
  "BoilerAlert": { "MaxContinuousHours": 4.0 },
  "TemperatureBand": { "MinCelsius": 5.0, "MaxCelsius": 30.0 }
}
```

Antifreeze wins over the program, over its suspension and over a manual switch-off. Notifications go to the subscribers of the `technical`, `heating` and `gates` topics; subscriptions are explicit for every user, admins included.

### Gate access

```json
"Gates": { "RateLimit": { "MaxOpenings": 3, "WindowMinutes": 10 } }
```

The limit applies only to users without `admin` or `gate_controller`. When a shared access window expires, the users who used the gates receive a notice.

### Touch panel

| Port | Bind | Purpose |
|---|---|---|
| 5050 | `0.0.0.0` | REST API, MCP and sensors, protected by `X-Api-Token` |
| 5051 | `127.0.0.1` | kiosk panel; the machine token is injected into `config.js` |
| 5052 | `0.0.0.0` | LAN panel; authorised devices use an HttpOnly session cookie |

`/panel` answers 404 on 5050 and is unreachable from the LAN on 5051.

Devices are authorised per device, never by client IP or hostname:

1. Open **Dispositivi › Aggiungi dispositivo** on the panel, or run `./panel-pair.sh "iPad cucina"` on the Pi.
2. Scan the QR code, or open the printed link, on the device.
3. The device receives an HttpOnly cookie valid for `SessionDays`; revoking it removes the device from the list, frees the name and invalidates the cookie immediately.

The QR is returned once and never stored: the database keeps only the hash of the single-use link. Generating a new link invalidates the previous one. `Panel:LanHost` must be a stable name or reserved address (for example `poderebot.local`), because the cookie is bound to the Pi origin: if the address changes, the device must pair again.

```json
"Panel": {
  "LanPort": 5052,
  "LanHost": "",
  "AllowLan": true,
  "PairingMinutes": 10,
  "SessionDays": 30,
  "History": { "SampleMinutes": 5, "RetentionDays": 365 },
  "Events": { "RetentionDays": 30, "MaxEntries": 500 }
}
```

`panel.db` holds the hourly temperature history (average, minimum, maximum and sample count per hour), the event log and the paired devices. LAN traffic is plain HTTP: acceptable on a trusted network for testing, while production should use HTTPS or Tailscale.

The panel keeps working when Telegram is down: `/api/health` reports the core (database) and `telegramOk` separately, and the watchdog restarts the service only when the core fails.

### API

`GET /api/status`, `/api/temperatures`, `/api/heating`, `/api/gates`, `/api/health`; `POST /api/temperature`. `/api/health` answers 200 while the core (the writable database) is healthy and reports Telegram separately as `telegramOk`; it is what the systemd watchdog checks, so a Telegram outage never restarts the bot.

`install.sh` generates `API_TOKEN` in `.env` when it is missing, and the app then requires the `X-Api-Token` header on every `/api/*` and `/mcp` request. Clear the value in `.env` only if you deliberately want the local-network restriction to be the only guard.

Users are the `Users` seed in `appsettings.json` merged with the gitignored `users.json`, minus the ids under `Removed`. Each entry has `Id`, optional `Name`, `Entitlements` and `Topics`. The entitlements are `admin` (implies every other entitlement) and `gate_controller` (opens the gates at any time, without being an admin). The topics are `technical`, `heating` and `gates`, and they are explicit for every user: a new admin starts with all three and can remove them. A user with no entry, or with no entitlement, is a normal user. `/adminpanel` (admin only) lists them as Telegram contacts and manages entitlements and topics; changes persist across `patch.sh`. A legacy `admins.json` is migrated once and then deleted. Admin commands are hidden from non-admins.
